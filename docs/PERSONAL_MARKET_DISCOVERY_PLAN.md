# 面向本人目标的 A-Atlas 方案与行情计划

日期：2026-10-02。代码审查基线：`82aa900`。
状态：用户于 2026-10-02 明确要求落地并开始执行；M1 已实施，任务与验收见
`docs/MARKET_DISCOVERY_IMPLEMENTATION.md`。M2 工程已上线、收盘对账通过，盘中实测与源端量比基准
仍待验收（`docs/MARKET_DISCOVERY_M2_REPORT.md`）；M3 已按收盘快照范围交付（`docs/MARKET_DISCOVERY_M3_REPORT.md`），M4 待本人真实使用；不宣称数学意义上的绝对最优。

## 用户目标与结论

目标：服务本人，用自然语言从 A 股找到想要的那类股票。
本轮明确的行情范围：**当天涨跌、成交额、放量等排行，并能叠加业务条件。**

目前产品形态合适，但现有实现还不是满足该目标的最佳方案。主要缺口是行情时间/刷新、
组合查询覆盖及结果资格；增加更多页面、模型或通用 Planner 不是这些缺口的直接解法。

建议保留发现页、公司卡、物理交互、事实 corpus、唯一 Jev judge 与 Web + Data 两组件。
在现有项目上完成“实时或盘后行情事实 → 明确条件 → 全池数值过滤/排序 → 有证据的业务判断
→ 带时间与覆盖范围的结果”闭环。纯公司发现继续走现有检索路径。

## 已确认的工程缺口

1. 「今天领涨的公司」复现为正确的 `market-only / pctChange desc`，但市场日期为
   2026-09-28；旧快照的计算与排序正确，不代表今天可用。
2. `lib/market/state.ts` 的 manifest/rows 进程缓存不会主动重新读取更新后的文件；
   因而单独更新磁盘数据，不足以保证长期开着的 Web 使用新数据。
3. `discoverCacheKey()` 含交易日期，不含行情内容 digest 或 snapshot id；答案 LRU
   无 TTL。同一交易日内行情改变后，这种缓存不能支持及时更新的排行。
4. 「今天领涨的机器人公司」类 semantic-first 路径先取有限语义结果，再按行情排序；
   候选池外的业务符合公司可能被遗漏，不能证明这是该业务全池的头部。
5. 当前 quote 抽取函数没有保留源端报价时间，服务的 quote `asOf` 为空；
   `fetchedAt` 只能证明何时抓取，不能证明行情属于哪个时点。
6. 现有“20 日量比”是当日累计量 / 过去 20 个交易记录日的全天均量；盘中使用时
   不能把它当作已经完成的全天放量，也不能与源端标准量比混称。

证据位置：`lib/market/state.ts`、`lib/atlas/discoverCache.ts`、`lib/cache.ts`、
`lib/hybrid/execute.ts`、`lib/market/derive.ts`、
`services/stock-data/generated/stock_data.py`、`services/stock-data/server.py`。

## 行情事实链的目标契约

行情保持与 Company Corpus 隔离。同一次搜索固定一个 snapshot，不能边查边换批次。
每个 snapshot 至少有：snapshotId/contentDigest、目标交易日、源端行情时点、采集起止时间、
session（盘中/收盘/休市/尚未开盘）、来源、公司池版本、覆盖与缺失/过期/异常行计数。
全池分批采集并非同一毫秒成交快照，必须记录时间跨度；不能称为零延迟行情。

目标交易日由交易日历与交易阶段决定，不由“磁盘上最后一个文件”的日期决定。
来源时点必须可验证；时间缺失或采集跨日不能靠抓取时间补造。

市场休市时：「今日休市；以下为最近交易日 YYYY-MM-DD 的收盘榜单」。
交易中：使用已通过时间与覆盖校验的当前交易日快照，标明时点。
收盘后：使用当日收盘状态；尚未就绪时明确未更新，不悄悄改用前日回答当日问题。
午间与盘前也必须有明确阶段；不能把行情没动自动判定为来源坏了。

上交所 2026 年国庆休市为 10 月 1–7 日，10 月 8 日开市；据该安排推断，10 月 2 日
正常情况下应显示休市并使用 9 月 30 日收盘数据，而当前本地停在 9 月 28 日。
来源：[上交所休市公告](https://www.sse.com.cn/disclosure/announcement/general/c/c_20260915_10832273.shtml)。
生产实现要分别核验 SH/SZ/BJ 的交易日安排，而不是把本文示例当长期日历。

数据实现先复用已接入的 batch quote 与盘后日线来源；源的全池覆盖、源端时点、
延迟、缺失与稳定性仍须小规模试采再全池验证，不能仅凭 vendor 文档宣称实时可用。
如需上游新增时间字段，按 VENDOR 同步/机械抽取流程处理，不手工改 generated 文件。

更新由既有 Data service 负责：使用中的盘中短间隔共享刷新、过期请求合并、盘后增量更新，
休市不反复全池抓取。刷新间隔先作为可配置候选（例如 30–60 秒）试测后定，不承诺秒级。
不建立独立 scheduler 平台，不为每次搜索重复抓取全池，不新增后台第三组件。
新 snapshot 完成校验后原子发布；Web 按 snapshot identity 读缓存和答案缓存，更新无需重启。
冻结 benchmark 的历史输入与实时运行产物分开，历史基线继续可重放。

## “行情理解”要拆成三个可检查步骤

1. **时间理解**：今天是哪一个市场交易日，盘中还是收盘，数据是否已达到要求。
2. **指标理解**：领涨→涨跌幅降序，成交额→金额，换手率→百分比，放量→明确的量度及基准。
   现有可编译句法优先复用；真正含糊的条件给出澄清，不自动发明阈值。
3. **集合与操作顺序理解**：哪些公司满足业务，先过滤还是先截取 TopN，谁决定排序。
   语义由 Jev 判断，行情数值与排序由确定性代码执行；行业词不进入 grammar。

不增加预测涨跌、收益打分、通用 AI 研究或第二 judge。

首批字段限定为当前用户需求：当日涨跌幅、累计成交额、换手率、量比/相对成交量。
放量先提供源端有明确口径的量比排行，以及盘后相对既有历史均量的排行。
源端量比的基准与时点要核验；若缺失，不能拿另一量度静默代替。
盘中累计量相对历史全天均量可标作事实比值，但不能把低于 1 解释为全天缩量。
更复杂的“同时间段放量”需要历史分时数据，不在第一版顺手扩建。

## 组合查询的建议执行语义

### 业务集合内排行

「今天涨幅最高的 20 家机器人公司」：

1. 在固定完整行情快照上做数值条件过滤，按涨幅与稳定代码 tie-break 排序。
2. 沿该顺序分批调用既有 Jev capability 检查公司事实是否满足业务条件。
3. 找到 K 个可确认符合的公司后停止；或池耗尽、预算耗尽时停止。
4. 不按语义分再次改动行情顺序，不把弱相关等同确定满足业务条件。

如果前缀所有公司的业务资格都得到明确判定，才能在当前快照与 capability 判断范围内
确认该前缀的 TopK。高位有未决判断、数据缺失或扫描提前终止时，返回已确认结果并标
“已扫描 N 家/结果不完整”；不能称全市场穷尽。
扫描批量、预算与缓存需实测，窄业务可能扫描很多公司，不能预先保证所有查询都很快。
业务判定可按 query + corpus digest + capability contract + judge identity 复用，
行情 snapshot 变化不会使公司业务事实自动变化；缓存不得跨 corpus/身份版本复用。

这个方案适用于行情主导的组合搜索，不能直接替换纯公司发现算法。
实施会涉及既有执行/结果资格契约，必须单独标明变更并针对受影响查询验证。

### 全市场排行里的业务子集

「全市场成交额前 20 中，有哪些机器人公司」：先取全市场前 20，再检查其中的业务。
不足 20 个属于正确结果，不继续到第 21 名“补齐”。
不能把两种自然语言都编成相同的 limit→market-first 路径；无明确作用域时澄清。

纯行情查询直接执行数值过滤与排序，**零 Jev 调用**；纯业务发现仍走现有搜索系统。

## 最小产品呈现

保留物理牌堆与公司页。行情结果只补任务必需的信息：
“盘中截至 HH:mm:ss / YYYY-MM-DD 收盘 / 休市”、排序字段与方向、实际值、
识别出的过滤条件，以及影响榜单可信度的缺失/未决/扫描范围。
行情排行要有明确名次，浮牌位置不能让用户猜谁第一。
每家公司业务资格与行情数值各自有依据；公司页行情时点与搜索 snapshot 不一致时说明。
不增加一级行情导航、指数墙或研究工作台。

## 实施顺序与完成判据

| 里程碑 | 范围 | 完成判据 |
|---|---|---|
| M1 正确日期与更新 | 最新盘后日、交易日历、过期状态、刷新后的运行时/答案缓存 | 「今天领涨的公司」只使用目标日期的数据或明确未更新；更新后无需重启；纯行情零 Jev |
| M2 当天快照排行 | 同一 snapshot 的批量报价、时间/覆盖校验、涨幅/成交额/换手/量比 | 盘中与盘后标签正确，全部返回值与 snapshot 一致，顺序一致；部分覆盖不冒充完整榜单 |
| M3 业务条件叠加 | 业务内 TopK 与全市场 TopN 内子集的不同语义；有预算的顺序扫描 | 高行情排名、低检索排名的符合公司不会因原语义池截断漏掉；预算/未决诚实呈现 |
| M4 本人使用收口 | 本人的真实查询与 trace 复盘 | 确认实际找股任务完成，按失败原因做小步修复；不为凑阶段扩数据、指标或模型 |

不承诺固定工期：M1 可先交付；M2 取决于来源时间与覆盖是否能达标；M3 取决于扫描成本
与判断质量。源不达标时暂停盘中承诺，不用界面显示“实时”掩盖问题。

验证以数值/时点对账和操作顺序为主：节假日/盘前/午休/跨日/收盘未发布、
行情更新后的缓存、短行/缺失/停牌、TopK vs TopN 内子集、未决与预算结束。
合成 fixtures 要包括“语义候选池外的高涨幅业务公司”反例，避免只证明既有实现能跑。
只有 M3 涉及 Jev 行为时按受影响 family 做 targeted LIVE；M1/M2 不重跑全量 LIVE 基准。

使用观察期等待更多样本没有必要；本人明确需求已经存在。规则来源与实现边界仍要遵守。

继续固定输入。未新增语义 judge 或修改业务资格，未运行真实 Jev 搜索。后续按落地任务的闸门推进。
